01

The five-minute recap

Just enough shared vocabulary to make the comparison make sense.

Recap

LoRa mesh in one slide

  • LoRa - long-range, low-power radio on unlicensed 915 MHz
  • Mesh - nodes relay for each other, so range is the sum of the hops
  • Text, position, telemetry - bytes, not megabytes
  • No towers, no internet, no license - about $30 to start
Recap · vocabulary

"Routing" means two different things

Channel message · one → many

"Anyone on LongFast around?" Every node needs a copy, so there's no single path to pick.

Both projects flood these. The question is who relays.

Direct message · one → one

Only one node needs it, so the mesh can learn a path and keep everyone else quiet.

Both projects learn a path for these. The question is how.

So "Meshtastic floods, MeshCore routes" isn't quite right. Both do both.

  • Common misconception: "Meshtastic floods, MeshCore routes." Since 2.6, Meshtastic routes DMs by next hop, and MeshCore still floods channel messages.
  • The real differences: (1) which nodes relay at all, and (2) how a DM path is learned and carried.
Recap · Meshtastic

How Meshtastic moves a message

Channel · managed flooding

  • Each node that hears it rebroadcasts, spending one hop (3 default, 7 max)
  • Weaker signal = shorter wait, so distant nodes relay first
  • Nearer nodes that hear a relay stay quiet; routers always relay
  • Hearing a rebroadcast counts as the ACK

Direct · next-hop routing (2.6+)

  • The first DM floods
  • The reply shows who relayed it, so that node becomes the next hop
  • Learned hop by hop: after that, only the matching node forwards
  • No ACK? It retries through the same next hop. The last of up to 5 tries floods, in case a node moved or conditions changed.
  • Source: meshtastic.org/docs/overview/mesh-algo
  • Channel: SNR-based contention window. ROUTER / ROUTER_LATE rebroadcast even if they've heard someone else do it. A reliable broadcast is sent at most 3 times.
  • DM: the next hop is learned from a NodeInfo response, ACK or traceroute coming back through one of the original relays. A reliable DM is sent up to 5 times, and the recipient sends a real ACK.
  • Mixed firmware: if a node in between is older than 2.6, or the link is one-way, that hop just uses managed flooding. No flag day needed.
Recap · the catch

Where flooding starts to strain

Airtime

One channel, shared by everyone. Every rebroadcast is airtime nobody else can use.

Background chatter

Node info, position and telemetry flood too - often more than the actual messages.

Hop ceiling

Raising hops to reach further multiplies traffic for the whole mesh.

A mesh that works beautifully at 30 nodes can feel very different at 300.

  • This is the bridge slide: it sets up the "why does MeshCore exist" question without trashing Meshtastic.
  • Role misconfiguration (everyone setting ROUTER) is a good anecdote here if we have a local example.
02

Enter MeshCore

Same radios, same band, different idea of who should be talking.

MeshCore

Three kinds of node, three jobs

Companion

Your radio. Pairs with the phone app. Sends and receives - does not relay.

Repeater

Infrastructure. Placed deliberately, up high. The only thing that forwards traffic.

Room server

A bulletin board on the mesh. Holds messages so you can catch up after being offline.

Roles are a firmware choice, not a setting - you flash the node for the job it's going to do.

  • Contrast: in Meshtastic, a handheld in a pocket is a relay by default (CLIENT). In MeshCore it never is.
MeshCore

How MeshCore moves a message

Channel: flooded too, but only repeaters relay it

Direct:

  1. The first DM floods through the repeaters
  2. The reply carries back the whole path it took
  3. Later DMs carry that path, so only those repeaters forward them
  4. If the path breaks, it floods again and relearns

Or set it yourself: if you know the best route, pin a contact's path to specific repeaters.

  • Squares are repeaters, circles are companions.
  • The contrast with Meshtastic 2.6+: Meshtastic learns a next hop at each node along the way. MeshCore learns the whole path at the sender and carries it in the packet (source routing). VERIFY against current MeshCore docs.
  • The bigger practical difference is on the channel side: both flood, but in MeshCore companions never relay, so a flood only touches the repeaters.

Tradeoffs

Neither one is "the better mesh"

Meshtastic can be strong when…

  • The group is small, mobile, or ad hoc
  • There's no infrastructure and nobody to plan it
  • You want sensors, maps, MQTT, ATAK
  • New people need to be on the air in ten minutes

MeshCore can be strong when…

  • The mesh is large, dense, and mostly fixed
  • Someone is willing to site and maintain repeaters
  • Reliable messaging matters more than features
  • You want to choose the route a message takes
03

Inside the firmware

Same LoRa radio underneath. What each firmware does with it is where they really differ.

Firmware

What's encrypted, and who can read it

  • Channel messages: anyone with the channel key. A public channel's key is public, so treat it as public.
  • Direct messages: only the person you sent it to.
  • Routing info: left readable, so relays can forward a message without reading it.
  • Who sent a channel message: not verified. Anyone with the channel key can put any name on it.

Same idea on both. One difference: MeshCore nodes sign their announcements, so a node can't be impersonated. Meshtastic trusts the first key it hears for a node.

  • Both run on unlicensed ISM spectrum, which is why encryption is allowed at all.
  • If asked for specifics - Meshtastic: channels AES-CTR with the channel key, DMs X25519 + AES-256-CCM (meshtastic.org/docs/overview/encryption). MeshCore: Ed25519 identities and signed adverts, X25519 key exchange, AES-128 encryption with a 2-byte HMAC-SHA256 MAC (MeshCore docs/payloads.md and docs/kiss_modem_protocol.md).
  • Meshtastic has no forward secrecy: record traffic now and obtain the key later, and you can read all of it.
Firmware

What it sends when nobody's talking

Meshtastic · pushes

  • Node info, position and device telemetry go out on timers
  • Every node keeps a live picture of every other node
  • Each of those broadcasts floods like a message

MeshCore · pulls

  • Companions stay silent until you send an advert
  • Repeaters advertise every 12 hours by default
  • Status and telemetry are a request and a response, only when someone asks
  • This is the airtime story from the recap, seen from the firmware side.
  • Meshtastic intervals are configurable, and local groups often lengthen them. Ours: node info hourly (from the Tulsa deck's recommended settings) - confirm what OKC recommends.
Firmware

One firmware, or one per job

Meshtastic · one firmware + modules

  • Every node runs the same firmware; the role is a setting
  • Features are modules you switch on: MQTT, telemetry, Store & Forward, range test, serial, ATAK…

MeshCore · a build for each job

  • Flash the job: companion (your radio), repeater (relays) or room server (a message board)
  • Focused on messaging and reliable delivery, with fewer built-in extras

Catching up after being offline shows the split: Meshtastic adds a module (Store & Forward); MeshCore adds a node (a room server).

  • MeshCore companion firmware is also built per connection: Bluetooth, USB or Wi-Fi.
  • Room servers act like a BBS and push the last 32 unseen messages on login (MeshCore FAQ).

Anatomy of a site node

Custom E22-900M30S HAT (SX1262, up to 1 W) by Yury · PoE splitter · project box with a 3D-printed bracket · 32 GB SD · about $129 per node

One Ethernet cable from the Pi straight to the AREDN node carries both data and power.

  • Why a Pi for infrastructure when we tell everyone else to buy a $30 board: Ethernet, remote shell, logs, updates without climbing a roof, room for other services.
  • Those strengths only matter at a fixed, hard-to-reach site. In a pocket, the Pi's costs win: SD cards, power draw, more to go wrong.

Two nodes per site, one build

meshtasticd

  • Meshtastic's native Linux build - the real firmware, not an emulator
  • Configured like any node: app, CLI, or the web client over the network
  • Our router: PSBR on the physical science building

openHop Repeater

  • MeshCore repeater in Python (formerly pyMC_Repeater)
  • Web dashboard, plus admin login over the mesh
  • Its observer reports the MeshCore nodes it hears to the MeshCore Analyzer at analyzer.letsmesh.net
  • Phy Sci repeater: built, awaiting installation

Where we run both, it's two identical Pis at the site, one per protocol. Same parts list, same HAT, same pins. Only the software differs.

  • We monitor both Pis over AREDN: SoC temperature, throttling and under-voltage go to Home Assistant over MQTT, with node_exporter feeding Grafana for trends.
  • Why two boxes instead of one: a radio speaks one protocol at a time, and both services want the same SPI bus and GPIO pins.
  • One build for both means one parts list to stock and one set of spares.
  • Observer: openHop's mqtt_brokers section, iata_code OKC. Seen nodes show up on the MeshCore Analyzer at analyzer.letsmesh.net.
OKC infrastructure

Managing a node you can't reach

Meshtastic · who you are

  • The remote node stores the public keys of up to three admin nodes (2.5+)
  • Commands are only accepted if they come from one of those nodes
  • Android, iOS and CLI (--dest); the web client can't send them

MeshCore · what you know

  • Repeaters and room servers have an admin password, plus an optional guest password
  • Log in from any companion app, then change settings remotely
  • On openHop, we've seen over-the-air passwords cut at 15 characters; stock MeshCore may not do this

Keys can't be guessed or leaked in a group chat, but lose all your admin nodes and you're locked out - use all three slots.

A password is easy to share across a team, but it has to change when someone leaves.

  • Source: meshtastic.org/docs/configuration/remote-admin. Admin keys live in Security Config. --set security.admin_key appends a key; setting it to 0 clears the whole list. Over the CLI, only --set and --get work remotely.
  • Pre-2.5 nodes used a shared "admin" channel. It's legacy only, and a 2.5+ node can't be managed that way.
  • The Meshtastic docs warn that a bad remote setting can knock a node off the mesh. On a roof, that means a site visit - try it on a bench node first.

When the network isn't yours

Lookout Cay at Lighthouse Point, Eleuthera: the day the Wi-Fi quit.

A real day

Separated on an island

  • Disney runs Wi-Fi access points across the island, and iMessage usually gets through
  • My wife, a week after gallbladder surgery, took a golf cart in with our oldest daughter
  • The rest of us walked the pier and waited at the tram stop
  • Twenty minutes later: where are they?
  • Messages wouldn't send. That day, the Wi-Fi wasn't passing them.
  • Coverage on the island is never complete, but it's usually good enough. That's the point: "usually" isn't something you control.
  • A is the ship at the end of the pier, B the tram stop where the pier meets land, C the splash pad on the east beach - about 1.3 km from B. Same letters as the coverage maps coming up.
A real day

Twenty minutes of nothing

  • A couple of family members rode the tram in to look for them
  • We waited for a text saying they'd found them. Nothing came through.
  • We asked people coming off the same golf carts. Nobody had seen them.
  • So they must already be on the island. We headed for the tram too.
  • On a hunch, I had my phone forget the Wi-Fi network, then rejoined it. Now my messages to my dad, standing next to me, showed Delivered.
  • Play up the waiting. Everyone in the room has stared at a "Not Delivered" and wondered whose fault it was.
  • The rejoin fixed my side, but we still couldn't reach my wife. Don't explain why yet - that's the punchline.

The point

A network we control

One radio up high

Left on the top deck, it relays between the pier and the beach.

One in each pocket

A $30 node paired to each phone. The phone is only the keyboard.

Nobody else's network

No Wi-Fi, no cell, no iMessage. If our radios are on, we can talk.

A small family mesh like this is exactly where Meshtastic shines: every node relays, and there's nothing to plan.

  • Before suggesting anyone do this, check that 902-928 MHz is permitted in the Bahamas and what the cruise line's policy is on transmitters.
  • A stateroom balcony is lower than the top deck. If that's the realistic spot, re-run the coverage from there.
  • Callback: this is the "small, mobile, ad hoc" column from the tradeoffs slide.

The big question… would it have worked?

Say it straight, like the answer is obviously yes. Pause. Click.

The answer

Nope.

Her phone was in the front pocket of my backpack.

Her radio would've been right next to it.

A mesh can route around a network you don't control. It can't route around the human element.

  • I found it right before we got on the tram - after fixing the Wi-Fi, of course.
  • Pause for the laugh, then land the point: any network, theirs or ours, is only as good as the people carrying it. Charge it, carry it, and know who has which radio.

Still learning

What we're still figuring out

  • How does each protocol hold up as more OKC nodes come online?
  • Do we run both long-term, or does one win on its own?
  • What does a switch cost the people already on the mesh?
  • Which other sites are worth an infrastructure node?

The question isn't Meshtastic or MeshCore. It's what kind of mesh OKC wants to be, and who's willing to build it.
